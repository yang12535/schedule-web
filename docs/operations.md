# 运维说明

本文补充 README 之外的运行时行为与设计取舍，面向自托管（Docker 或裸机 node）的维护者。

## ICS 日历订阅：60 秒进程内缓存与限流豁免

`GET /api/calendar.ics` 是日历客户端的订阅轮询入口，有两条专门设计：

- **豁免通用限流**：通用限流为 200 次/15 分钟/IP。全班同学常共享同一 NAT 出口，订阅客户端的自动轮询会与交互式 API 抢同一配额，容易集体 429，因此该接口不参与通用限流。单次导出开销已被「最多展开 30 周」封顶，不会成为 DoS 放大器。
- **60 秒进程内缓存**：豁免限流后仍需压住单源洪峰的 CPU 放大。订阅 URL 固定、无查询参数，60 秒 TTL 内的重复请求直接命中缓存；任何写操作成功落盘时缓存立即失效，下次导出即为最新数据。缓存响应的 `DTSTAMP` 最多滞后 60 秒——日历客户端以 UID 判重，不受影响；直接手改数据文件的最坏可见滞后同样不超过 60 秒。

该接口始终返回 `Cache-Control: no-cache`：短 TTL 缓存只是服务端的生成开销优化，客户端每次仍会回源校验。

## 时区：`TZ=Asia/Shanghai` 是前置要求

ICS 事件时间与日志时间戳按服务器本地时区生成、以 Asia/Shanghai 语义解释。Docker 镜像已内置 `TZ=Asia/Shanghai`；裸机 `node server.js` 部署时必须自行设置：

```bash
TZ=Asia/Shanghai node server.js
```

时区不符时课表时间会整体偏移。服务启动时会检测本机时区，不是 Asia/Shanghai 即打印告警（测试环境除外）；看到该告警请先修正时区再投入使用。

## `TRUST_PROXY=true` 的前提：反向代理必须清洗 XFF

限流与请求日志都以客户端 IP 为键。默认（不设置 `TRUST_PROXY`）只认 TCP 对端地址，请求自带的 `X-Forwarded-For`（XFF）头一律忽略——这是安全默认：服务直接暴露时，客户端可以任意伪造 XFF 来绕过限流、污染日志。

只有当服务位于**自己控制的反向代理之后**（nginx、Caddy、云负载均衡等），且该代理会**覆盖**客户端传入的 XFF（而不是追加或原样透传）时，才设置 `TRUST_PROXY=true`。此时服务取 XFF 第一个 IP 作为客户端地址。

若代理不清洗 XFF，攻击者伪造一个随机 XFF 头即可让每个请求看起来来自不同 IP，等同关闭全部 IP 限流。不确定代理行为时，保持默认（不设置）更安全。
