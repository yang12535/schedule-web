# 运维说明

本文补充 README 之外的运行时行为与设计取舍，面向自托管（Docker 或裸机 node）的维护者。

## ICS 日历订阅：60 秒进程内缓存与限流豁免

`GET /api/calendar.ics` 是日历客户端的订阅轮询入口，有两条专门设计：

- **豁免通用限流**：通用限流为 200 次/15 分钟/IP。全班同学常共享同一 NAT 出口，订阅客户端的自动轮询会与交互式 API 抢同一配额，容易集体 429，因此该接口不参与通用限流。单次导出开销已被「最多展开 30 周」封顶，不会成为 DoS 放大器。
- **60 秒进程内缓存**：豁免限流后仍需压住单源洪峰的 CPU 放大。订阅 URL 固定、无查询参数，60 秒 TTL 内的重复请求直接命中缓存；任何写操作成功落盘时缓存立即失效，下次导出即为最新数据。响应的 `DTSTAMP`/`LAST-MODIFIED` 取数据文件 mtime（见「HyperOS 超级岛」节），数据不变时缓存重建前后输出逐字节一致；直接手改数据文件的最坏可见滞后不超过 60 秒。

该接口始终返回 `Cache-Control: no-cache`：短 TTL 缓存只是服务端的生成开销优化，客户端每次仍会回源校验。同时返回 `Last-Modified`（= 数据文件 mtime），与随输出稳定的 ETag 一起让 `If-Modified-Since`/`If-None-Match` 条件请求在数据未变时返回 304——no-cache 要求每次回源，304 免去的是响应体重传，两者不冲突。

## HyperOS 超级岛日历提醒刷屏

**根因**（M32 调研，2026-09-25，证据分级见调研存档）：本服务 ICS feed 此前每次重建缓存（60s TTL）都把全部事件的 `DTSTAMP` 刷成生成时刻，且没有 `SEQUENCE`/`LAST-MODIFIED`。按 RFC 5546 §2.1.5 的消息决胜规则，UID 与 SEQUENCE（缺省 0）相同时 `DTSTAMP` 是唯一的修订判据——变新即判「有新修订」。于是每次订阅同步，全部事件在客户端眼里都是「刚被修改」，提醒被重发；HyperOS 系统日历的日程提醒会上超级岛（小米官方上岛清单确认），同一日程被重复发帖 N 条通知即叠出 N 个岛。ICSx⁵ 系客户端另有同效路径：VEVENT 无 `LAST-MODIFIED` 时每次同步无条件重写本地事件（含提醒）。早期「超级岛 `updatable=false` 导致叠加」的说法经核查不成立：该字段是第三方应用接入焦点通知的 API 参数，不影响重复发帖本身；真正要堵的是上游的伪事件更新。

**本次修复（M34，根修）**：`DTSTAMP` 与每个 VEVENT 新增的 `LAST-MODIFIED` 统一取数据文件 mtime——数据不变时两次导出逐字节一致：iTIP 系客户端不再判更新，ICSx⁵ 系按 `LAST-MODIFIED` 跳过未变事件，ETag 随之稳定，`If-None-Match`/`If-Modified-Since` 条件请求返回 304（多数客户端连下载都跳过）。同时去掉了 `METHOD:PUBLISH`：轮询订阅 feed 不是 iTIP 消息，且原输出无 ORGANIZER 违反 RFC 5546 §3.2.1；去掉后 `DTSTAMP` 语义回落为「最后修订」（RFC 5545 §3.8.7.2 无-METHOD 分支），与 mtime 取值自洽。数据真变（任何写操作落盘）时 mtime 更新，客户端正常看到一次真实更新。

**一次性重发波预期**：部署本修复（及 M31 VALARM 剥离）改变了 feed 内容，客户端首次同步会看到一次真实的全量更新，可能重发一波提醒——属正常现象，不应误判为修复失败；下个同步周期起应恢复平静。

**M31 减面开关**：`ICS_SLOT_SUMMARY_ALARM` 控制 📋 时段汇总事件是否携带 VALARM，默认 `false`（剥离）。汇总事件（上午/下午/晚上每天最多三发，提醒时刻 = 该时段首课开始前 60 分钟）原是最大提醒面，剥离缩小重复提醒规模；单节课事件（含补课）的间隙自适应提醒（`-PT10M`/`-PT30M`）不受影响。VALARM 不参与 UID 哈希，开关两态下全部事件 UID 不变，既有订阅无扰动。确需恢复旧的汇总提醒时设为 `true`。

**残余风险与客户端兜底**：若个别客户端「每次同步无脑全量重排」（连字节一致都不放过），服务端无解——但 ETag 304 生效后多数客户端连下载都会跳过，可最大化规避。部署后让受影响用户观察 1-2 个同步周期，仍刷屏即属此类，可用 `*#*#284#*#*` 抓 284 log 留证；止血手段是在 HyperOS 通知设置里关闭日历 App 的焦点通知（超级岛）权限，日历的普通提醒通知不受影响。

## 时区：`TZ=Asia/Shanghai` 是前置要求

ICS 事件时间与日志时间戳按服务器本地时区生成、以 Asia/Shanghai 语义解释。Docker 镜像已内置 `TZ=Asia/Shanghai`；裸机 `node server.js` 部署时必须自行设置：

```bash
TZ=Asia/Shanghai node server.js
```

时区不符时课表时间会整体偏移。服务启动时会检测本机时区，不是 Asia/Shanghai 即打印告警（测试环境除外）；看到该告警请先修正时区再投入使用。

## `TRUST_PROXY=true` 的前提：反向代理必须清洗 XFF

限流与请求日志都以客户端 IP 为键。默认（不设置 `TRUST_PROXY`）只认 TCP 对端地址，请求自带的 `X-Forwarded-For`（XFF）头一律忽略——这是安全默认：服务直接暴露时，客户端可以任意伪造 XFF 来绕过限流、污染日志。

只有当服务位于**自己控制的反向代理之后**（nginx、Caddy、云负载均衡等），且该代理会**覆盖**客户端传入的 XFF（而不是追加或原样透传）时，才设置 `TRUST_PROXY=true`。此时服务取 XFF 第一个 IP 作为客户端地址。

若代理不清洗 XFF，攻击者伪造一个随机 XFF 头即可让每个请求看起来来自不同 IP，等同关闭全部 IP 限流。不确定代理行为时，保持默认（不设置）更安全。

## 课程 id 回填（历史数据迁移）

2026-09 之前的数据文件课程对象没有 `id` 字段，而前端按 `data-id` 定位课程，缺 id 时编辑/删除会静默失效。服务在加载（`loadSchedule`）与保存（`saveSchedule`，唯一写出口）时为缺 id 的课程生成确定性 id（容器 + 课程内容哈希），并在首次加载旧数据时把回填结果落盘一次。回填幂等：同一份数据重复加载结果不变。ICS 订阅的事件 UID 由课程内容哈希派生、不含 id，回填不影响既有订阅。

### 已知限制：回填落盘与并发写存在理论竞态

首次加载旧数据时的回填落盘发生在**无锁读路径**上（`loadSchedule` 内，`server.js` 回填写盘处）。若同一毫秒级窗口内恰好有写请求竞争，该写请求的更新可能被回填落盘覆盖而丢失（尽管写接口已返回成功）。

判定为可接受、不予修复，理由：

- 窗口每份旧数据生命周期仅出现一次（升级后第一次加载），宽度毫秒级；
- 即使撞上，回填也只触发这一次——之后加载命中已回填数据不再改写，缓存与磁盘恢复一致（自愈），不会持续分叉；
- 本服务面向单用户/班级部署，「升级后首次加载的同一毫秒内恰有写请求」实际不可达；
- 不能简单用 `withSaveLock` 包裹修复：各写端点在锁内调用 `loadSchedule`，会形成自死锁；改造锁结构的复杂度与风险远超该窗口的实际影响。
